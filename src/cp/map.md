# map.md — src/cp/ (in-enclave control plane)

The control plane runs inside the enclave. All
of this runs in the one attested binary; handlers call the data-plane query/storage code
([`../search.rs`](../map.md), `../timeline.rs`, `../episodes.rs`, `../ingest.rs`) in-process
— no HTTP hop. Routes are wired in [`../main.rs`](../map.md).

| `control_store.rs` | Provider-neutral identity mappings, the service-wide daily signup budget consumed transactionally with each new account and its content-free `signup_v1` created/refused observations, encrypted per-Apple-client refresh authorization, per-device APNs installation registry with account rebind/token-generation fencing and deterministic cap, and identity/account deletion state in the context-bound encrypted SQLite blob `control/control.db.enc`. The same blob contains the inactive ADR-0022 bounded lifecycle anchor plus a separately versioned initial-witness protocol row enrolled atomically with each new reservation. That row binds archive/attempt, optional exact prepared witness hash/length, admitted revision, monotonic send phase, deletion fence, and a domain-separated commitment; candidate-free reservation/objects-prepared deletion is an explicit all-`None` tuple. Firestore send-start and account deletion serialize through this state: deletion distinguishes provably unstarted from started/ambiguous dispatch, while missing/unknown enrollment is permanently manual. A private exact-`None` capability can CAS absence, while any later present/invalid observation irreversibly poisons it to admission-free manual; exact existing send-start recovery atomically adopts the retained candidate as present. The blob also retains exact retry-stable bootstrap/witness bytes, monotonic create admissions, and mutually exclusive normal Tombstoned-witness versus pre-witness absence inventory snapshots/seals. The pre-witness tables bind the full protocol/bootstrap/fence/revision tuple and create-ahead commitment, including a zero-page terminal. On that branch the shared page ledger recomputes the exact deterministic plan for every admission/recovery/reconciliation, accepts only its exact prefix and optional unresolved next page, and rejects every page for the zero-object plan. Only coordinator-private authenticated plans can seal either branch. A separate versioned pre-witness execution row revalidates that exact branch and complete authenticated object set, binds one random operation ID, and full-row-CASes the strict registry/object/drain evidence stages while leaving the lifecycle anchor sealed. A separate inactive maintenance-import family binds one active archive to an opaque operation/owner/session, permanent legacy fence, exact source generation/hash/length/schema/DEK-metadata commitment, exact witness lease, retained R1/parity/R2 evidence, up to 16 immutable attempts, and at most 32,898 exact retained artifact rows per attempt. The dedicated R2 attempt is selected before ShadowWal-bound reconciliation; same-fence empty/reserved/materialized prefixes reopen without burning another attempt, while a full-tuple-validated higher-fence reacquire supersedes a partial attempt and resets its prefix. Renewal/reacquire CAS also matches the exact previous witness bytes, fence, and expiry; the Phase-2 succession persist additionally requires an intact `phase2_acquired` acquisition row for the same operation and — for a fresh succession — a basis hashing exactly to that row's terminal witness hash, superseding any partial R2 prefix like a higher-fence reacquire. That persist still compiles but cannot run: `Phase2AcquisitionStage` kept `from_db` and lost `as_db`, so an acquisition row written by an earlier build still decodes while no new one can be minted. Every capability-bearing maintenance mutation uses cancellation-safe owned-handle persistence; no startup or route produces its plan. A read-only loader surfaces the maintenance operation resting at the durable `wal_authoritative` terminal for one archive (any other stage refuses content-free), for the startup relaunch's handoff reconstruction. A read-only sealed per-user WAL-authority persistence selection is mintable exactly from the durable `wal_authoritative` terminal of the user's actively bound archive (the per-user loader requires an active account; the startup scan enumerates every ACTIVE-binding terminal user status-independently, revalidating each candidate in the same read transaction and failing the whole scan closed on any refusal — tombstoned bindings are excluded in the scan itself, because deletion tombstones the binding early while the terminal import row survives the deletion window, and an unfiltered candidate would fail the whole scan and panic startup before the reconciler that clears it can run), and only the Store's install-once selection consumer can use it. Eight advisory/Phase-2 tables survive as **DDL only** — `archive_v3_advisory_canary_scopes`, `_activation_preconditions`, `_owners`, `_releases`, `_comparisons`, `_aborts`, `_controller_runs`, and `archive_v3_phase2_authority_acquisitions` — together with the `migrate_advisory_abort_locus` column migration; both are applied on every control-DB open, because dropping a table without its migration in the same commit bricks every replica on startup, and schema removal is deliberately a separate atomic PR. `#289` (`9b2f87e`) deleted the code that wrote them, and **no writer survives outside tests**, so in production all eight are permanently empty. The Phase-1 advisory-owner reservation/CAS ladder that drove those rows is gone with the rest of the family. What still executes against them is read-only: `ensure_advisory_release_absent` (a live gate on the surviving import path that can no longer fail), the four existence checks in `abort_pre_owner`, and the acquisition and controller-run readers. Its separate release row kept its `Prepared -> DeleteStarted -> Released` DDL, but the ledger that drove those transitions — the Store-token-minted exact marker/generation and exact-name absence evidence — was deleted in `#289`. Prepare permanently fences lease advancement; maintenance plan re-adoption and post-lifecycle-lock entry reject a started release before provider I/O. The retained one-user Store target exact-authenticates and deletes only the recorded marker generation and reconciles loss only by exact-name absence. A separate terminal transition freshly reauthenticates the exact witness/release under that lifecycle lock and reopens both local legacy gates together; maintenance checks release before closing them, so stale work cannot reblock the user. It returns no connection, capture, or serving authority. Separate v1 WalAuthoritative-owner lease and checkpoint families bind the exact released maintenance terminal, owner identity, full expected/leased witness tuple, and a monotone Prepared/SourceReady/Uploading/CandidateReady/SendStarted/Witnessed/Manual protocol. Checkpoint attempts are capped at 16 and exact-AAD immutable artifacts at 32,898; reserve and every candidate/send/terminal load recompute the full deterministic interleaved chunk/manifest/root topology. The shared lease manager preserves same-fence attempts, supersedes only pre-send work after an authenticated higher-fence reacquire, and never mutates a SendStarted attempt. Unresolved logical publication is mutually exclusive; exact witnessed predecessor publication consumption, checkpoint witness settlement, and owner binding advance are one transaction. Each capability-bearing flush removes the sole SQLite handle from the shared cache until durable conditional PUT or exact lost-response readback; interruption leaves the cache empty so recovery reloads authoritative provider state. Producer-private recovery reconstructs bootstrap and sealed/physical receipts, but no destructive producer or runtime wiring activates the execution protocol. It also holds accounting, protected cost reservations, ADR-0032's bounded user-scoped reference-batch receipts plus their existing per-event delivery authority, webhook destinations/secrets, OAuth clients/codes, refresh tokens, daily usage/Vertex ceilings, and the redacted query log; identity rebind and account deletion migrate or erase the batch rows with their account, and email equality never links providers. |
